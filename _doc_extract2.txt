MyMmorpg 项目合规性评估报告
手游大世界 / 二游后端服务器标准对照与改进方案
评估对象：MyMmorpg（Java 17 / Spring Boot 3 微服务后端）评估日期：2026年8月3日文档性质：架构差距分析与解决方案
一、评估结论（摘要）
结论：当前项目尚未达到商业级「手游大世界二游」生产后端服务器标准，但已具备较完整的垂直切片骨架与正确的领域边界，适合作为原型 / 演示 / 中小规模试运营底座，不宜直接作为大型开放世界二游正式上线环境。
综合符合度（按商业上线标准粗评）：约 45%～55%。

二、评估标准说明
本报告对照行业常见「手游大世界 + 二次元养成/抽卡（二游）」后端能力模型，从以下八类标准进行审查：
接入与实时通信：长连接、会话、断线重连、分区路由、移动网络适应性
大世界仿真：场景分区、AOI、实体所有权、实例生命周期、跨节点迁移
核心玩法域：战斗权威计算、养成、任务剧情、活动、排行、匹配
二游商业化：抽卡合规、商城支付、货币账本、月卡/通行证、对账补单
社交与社区：好友、聊天审核、公会/联盟、举报封禁
安全合规：鉴权、限流、反作弊、隐私合规、密钥托管
平台工程：容器编排、HA、监控告警、CI/CD、配置发布治理
数据与一致性：分库分表、迁移、事件可靠投递、幂等与对账

3.3 与标准差距总览
主要差距不在「再加几个玩法模块」，而在生产硬化：经济账本、大世界扩展、支付合规、反作弊、HA 运维与一致性保障。项目自身 DEPLOYMENT.md 已标注多项为演示级或计划中，与本评估一致。
四、分维度差距分析与解决方案
4.1 大世界实时能力
现状：具备 scene-service、AOI 雏形、Center 路由、迁移票据（session_ticket），支持 TCP/KCP。但缺少大规模无缝世界所需的分区、实体所有权、实例池、跨服事件调度。
不符合点：
无完整 Zone/Region 分区与动态扩缩容
无地图实例生命周期（创建/销毁/热切）与副本池
无生产级 AOI 网格与跨节点实体所有权转移
无世界 Boss / 天气时间 / NPC 调度 / 采集交互物完整体系
断线重连与连接迁移协议不完整
解决方案：
短期：固化「地图分线 + 场景节点 + 迁移票据」模型，补齐重连快照与踢线仲裁
中期：引入 Zone Coordinator（或增强 Center），管理实例生命周期与热点地图水平扩展
中期：AOI 网格分片，实体所有权按格子/实例绑定，迁移时序列化最小状态
长期：边缘接入层（网关集群 + sticky）与大区部署；世界事件走 MQ 广播 + 幂等消费
验收指标：单场景万级可见实体、跨节点迁移 P99 < 200ms、节点宕机可疏散
4.2 二游核心商业化与经济安全
现状：有抽卡（保底 Redis + 历史）、商城订单、沙箱/HTTP 支付验签、活动充值联动；文档明确生产禁用 Mock。但官方支付 SDK、对账账本、退款拒付、货币流水仍不完整。
不符合点：
无不可抵赖的货币/道具流水账本与抽卡审计链
官方微信/支付宝/App Store/Google Play SDK 未直连
缺补单、对账、退款、拒付、重复回调处理闭环
缺月卡、通行证、首充、礼包限购等成熟商业模型的完整状态机
抽卡概率公示、版本不可抵赖、监管地区合规不足
解决方案：
建立 WalletLedger / ItemLedger：每笔增减带业务单号、前后余额、操作者、幂等键
支付订单状态机：CREATED → PAID → DELIVERED → REFUNDED，配合 Outbox 发货
接入渠道正式验签 SDK；生产强制关闭 Mock；回调去重 + 签名窗口
日终对账任务：渠道账单 vs 本地订单 vs 发货记录，差异工单
抽卡：持久化 Banner 版本、概率表哈希、每次抽卡 RNG 审计字段；支持监管导出
发奖统一走 GrantPort + 幂等表，禁止各服务直接改背包
4.3 战斗与养成权威性
现状：battle-service 支持战斗/Buff/挑战/肉鸽与 Redis 状态；技能支持 Groovy 策略。更像服务端逻辑示例，缺多角色编队、确定性校验、录像防篡改。
不符合点：
缺养成深度：角色/武器/圣遗物词条、元素反应、体力等常见二游体系
缺战斗确定性版本化公式与录像校验
缺高并发副本实例池与战斗重连
解决方案：
战斗配置版本号强制绑定；结算只信服务端结果
关键战斗路径增加动作频率校验与不可能状态检测
录像摘要入库供客服/反作弊抽检；配置与客户端资源兼容矩阵
养成数据独立表结构与强化流水，避免只改角色 JSON
4.4 社交、公会与内容生态
现状：好友、邮件、聊天、排行、匹配已有；公会/联盟、家园、成就图鉴、敏感词与举报闭环缺失。
解决方案：
优先补：敏感词服务、举报/禁言/封号、聊天频道分级与限流
二期：公会实体、权限、仓库、公会任务/战；组队状态机
三期：成就/图鉴/好感度；全服邮件与补偿投放工具
4.5 安全、鉴权与反作弊
现状：网关鉴权、会话 RSA、内部 HMAC、Admin 白名单与操作日志、网关限流均已具备，方向正确。
不符合点：
缺设备指纹、Root/模拟器检测、客户端完整性校验
缺行为风控（移速异常、经济异常、工作室识别）
Admin 缺 SSO/MFA/审批流；密钥多为环境变量，无 KMS 轮换
内部服务缺 mTLS / 独立服务身份
解决方案：
接入层：WAF + 多维限流（IP/账号/设备/接口）+ 登录风控
建立 RiskEngine：特征入库，自动降权/验证码/封禁策略
密钥进 Vault/云 KMS；支持轮换；Admin 上 OIDC + MFA
服务间逐步升级到 mTLS 或 SPIFFE；保留 HMAC 作过渡
4.6 平台工程与可观测性
现状：docker-compose（MySQL/Redis/Nacos）、GitHub Actions CI、Actuator/Prometheus 端点齐全；无 K8s/Helm、无完整监控大盘、无 CD。网关端口文档（8080）与配置（8443）不一致。
解决方案：
补齐 Kubernetes（Deployment/HPA/PDB/NetworkPolicy）+ Helm；分环境 values
MySQL 主从 + 备份 PITR；Redis Sentinel/Cluster；RocketMQ 高可用集群
Prometheus + Grafana + Loki + Tempo/Jaeger；定义 SLO（登录成功率、发奖延迟、MQ 积压）
CD：镜像构建扫描、灰度发布、一键回滚；统一文档与配置端口
引入 Flyway/Liquibase，禁止依赖 ddl-auto 或仅靠 init SQL
4.7 消息一致性与弹性
现状：设计了 PLAYER/BATTLE/SHOP/ACTIVITY 等事件；开发默认 RocketMQ=false + NoOp，存在「本地看似成功、异步未消费」风险。
解决方案：
生产强制 MQ；本地可用 Testcontainers 模拟，避免 NoOp 掩盖缺陷
关键写路径（支付发货、战斗结算投影）上 Outbox；消费端 Inbox 幂等
DLQ、重试退避、告警；定义补偿 Saga（支付成功发货失败可重试发放）
混沌演练：Redis 宕机、MQ 重复、域服务不可用时的降级与恢复手册
4.8 LiveOps 与内容治理
现状：活动/任务/商城/更新清单可导入校验，支持分阶段 reload 与发布审计，已超过一般 Demo。
解决方案：
配置生命周期：Draft → Review → Staged → Published → RolledBack
灰度：按渠道/分群/百分比；依赖校验与 dry-run
不可变发布包（配置 + 资源 checksum）与兼容矩阵
高危操作双人复核；完整操作审计不可篡改存储
4.9 测试与质量
现状：约 90 个测试类，CI 含集成环境；JaCoCo 最低行覆盖约 10%，对含支付/背包/抽卡的系统过低。
解决方案：
核心经济与鉴权路径覆盖率提升至 ≥70%，支付/发奖属性测试
补充压测（登录、进场景、抽卡、发奖）、协议模糊测试、迁移失败注入
合同测试（Feign/Internal API）与多版本客户端兼容测试

六、是否符合标准的最终判定
1. 对照「教学/毕业设计/架构演示」标准：符合。模块齐全，文档诚实，双模式架构清晰。
2. 对照「小规模封闭测试 / 技术预研服」标准：基本符合，需完成 P0（账本、MQ、监控、密钥、支付关闭 Mock）。
3. 对照「商业手游大世界二游正式运营后端」标准：不符合。缺失大世界扩展、经济账本与支付闭环、反作弊、HA/K8s、公会与深度养成、完整 LiveOps 治理。
建议定位：将本仓库作为「可演进的领域骨架」，按第五章路线图硬化平台能力，而不是继续横向堆更多玩法 Demo。
